## Architecture Overview

```
User Input
    |
    v
+---------------+     +--------------+     +---------------+
|  Components   |---->|  gameStore   |---->|  GameEngine   |
|  (React UI)   |     |  (Zustand)   |     |  (core/)      |
+---------------+     +--------------+     +---------------+
                           |                      |
                           v                      v
                    +--------------+     +---------------+
                    | engineAware  |     | EventProcessor|
                    | Setter       |     | (apply events |
                    | (sync state) |     |  to state)    |
                    +--------------+     +---------------+
```

**Action flow:**
1. Component dispatches action via `gameStore`
2. `engineExecutionBridge` forwards to `GameEngine`
3. `ActionDispatcher` routes to appropriate `Resolver`
4. Resolver returns `GameEvent[]`
5. `EventProcessor` applies events to `EngineState`
6. `gameStateAdapter` syncs engine state back to Zustand store

## Data Import Flow

**There is no per-card data store.** Every official general is one line in `src/data/generals.ts` (the central ledger); the 52 non-general cards live in `src/data/cards.ts`. Player-facing edits are **read-time overlays persisted in localStorage** (`store/editorPersistence.ts` keys: skill edits, general edits, disabled generals, identity registry) -- the source file is never rewritten, so old saves need no migration and official content is always versioned with the code.

Excel is a **bulk-edit surface for skills**, not an import path into a registry:

```
.xlsx file
    |
    v
+------------------------------+     +---------------------------+
| components/SkillEditor.tsx   |---->| skills/skillExcelFormat.ts|
| (read: XLSX.read + sheet_to_ |     | (3-col v1 / 6-col v2 rows |
|  json; write: exceljs)       |     |  <-> Skill effects)       |
+------------------------------+     +---------------------------+
            |
            v
   localStorage overlay -> merged into the pool at read time
```

- **Adding an official general = editing `generals.ts`** (plus a structured `SK_*` payload when the skill must actually resolve), which is why content cuts run the five gates and re-baseline the anchor.
- **Content ownership is decided by who wrote the field, not by which file it sits in (ruled 2026-10-05, PROJECT_HANDOFF §12-106 → corrected same day §12-107).** Two quotes, in order: 「你自己生成的技能内容，可以随便更改，但是不能更改我的官方将领技能」 and 「关平【龙吟】的卡面文字也是你生成的，可以改」; when asked which line to draw, the user chose **「按谁写的划」** (by authorship). So the protected set = **fields the user authored** — the roster rows added in the 2.0.0 commit `540bd7b`, i.e. `createGeneral(id, name, faction, maxHp, [skillNames…], title)` — plus any skill whose *meaning* comes from the user's own reference table or words. Changing those still requires a quote from the user in the current turn. The freely-editable set = **what I generated**: the printed skill descriptions in `src/data/generals.ts` and their effect payloads (type / value / target / trigger / gate / badges). Measured, not asserted: the file's 39 description lines dedupe to **37 unique strings**, and each one's first-introducing commit is a content-era cut — `1262a4d`×19, `f961b26`×9, `b154463`×3, `487e024`×2, `156cb21`×2, `d1acb3e`×1, `d748083`×1; `git show 540bd7b:src/data/generals.ts` contains **zero** `const SK_` blocks ⇒ nothing historical needs rolling back. Two obligations ride along: **every such edit must be registered** (which line changed and why — CHANGELOG + both histories), and wording may be re-worded to be more accurate while the *semantics* of a user-specified skill are a gameplay knife (three-gate protocol), not a text fix. Provenance recipe: `git log --reverse -S"<the exact description literal>" -- src/data/generals.ts | head -1` — **never** search the skill *name*, names were in the 2.0.0 roster and that leads back to the user with the wrong answer (§12-107⑤). Consequence for the long-standing open item: 关平【龙吟】's printed line is now **editable**, and the user chose **「暂不改，保持现状」** — recorded as "may change, deliberately not changed", not as "may not change". The v2.8.6 three-layer lock (whether a *player* may edit an official card in the UI) is a different, still-standing rule.
- **Coverage readings are registered as a range plus which run produced it (ruled 2026-10-05, §12-106③)** — e.g. `Stmts 63.9–64.2（同树 7 趟，登记第 7 趟）`; a single run is written honestly as 单趟、无区间. The floors (42/34/34/47) and the `exit 0` gate are unchanged, and coverage remains **not** an anchor criterion (§12-58④). Old registrations are not rewritten; both copies of the process doc carry the new format.
- The old "one file / one record + importer writes into a registry" scaffolding (`importer/`, `data/registries/`, `data/examples/caoCao.json`, `skills/dataSkillExamples.ts`, `data/types.ts`) was **deleted at v2.8.2** after being verified consumer-free; a content-package format for sharing player-made content is a future cut (see PROJECT_ARCH_MAP §G).
